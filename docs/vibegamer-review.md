核查日期：2026-10-19。参考仓库：项目上层的 `references/VibeGamer/`，核查版本：`201e103fe6e3ea70424ff3973574caba552031e5`。

范围：源码与说明书核查；未安装依赖，未运行游戏、模型或验证脚本。以下“已实现”表示找到实现，运行效果尚未在本机验证。

## 结论

有完整的策略存储、使用、验证、退役设计。适合借鉴经验管理，不能直接作为安卓执行器。优先借鉴局部技巧 Tip；整套游戏实验调度暂不搬入工作台。

## 策略怎么存

每个学习会话保存到 `agents/turmoil/memory/sessions/<sessionId>/`，以 JSON 保存当前状态，以 JSONL 追加过程记录。

| 内容 | 保存位置 | 用途 |
| --- | --- | --- |
| 整局策略假设 | `hypotheses.json` | 策略、依据、适用条件、状态、验证结果、重试额度 |
| 局部技巧 | `tips.json` | 触发条件、动作、范围、预期效果、评价指标、限制与证据 |
| 每局结果 | `games.jsonl` | 将收益、地图、所用策略关联到具体对局 |
| 变更记录 | `iterations.jsonl` | 谁改了什么、为什么改、修改前后内容与校验值 |
| 对照试验计划 | `tip-manifests/` | A/B，以及必要时C组，记录每次试验的角色与进度 |
| 精简策略手册 | `skills/best_skill.md` | 后续对局优先读取的经验摘要 |
| 策略历史版本 | `skills/vN.md`、`manifest.json` | 候选、当前采用版本、淘汰原因和回退 |

Tip 的重要字段：`decisionKey`（同类决策）、`trigger`（何时触发）、`action`（做什么）、`scope`（适用范围及排除条件）、`guardrails`（限制）、`evidence`（机会、执行、正负结果、近期效果）。

状态能区分候选、实验中、正式使用、仅特定条件有效、暂存、未确定、否决、被替代。没有通过验证的想法不会全部自动变成正式经验。

## 策略怎么用

1. 日常对局优先读取精简手册；没有手册则读取已验证假设。
2. 局部技巧按状态筛选、可信度排序，并限制加入提示词的文字量；精简手册模式默认最多附加两条 Tip。
3. 模型收到技巧的触发条件、适用范围、动作与预期效果，再判断当前是否适用。
4. 执行动作可附带策略编号，让记录能对应“用了哪条策略，结果如何”。
5. 失败反例可加入后续提示；近期表现变差的技巧可降级。

这是状态筛选、排序、提示词加入机制。所核查的注入路径没有按手机截图进行相似页面检索，也没有向量检索。Tip 的触发条件主要由模型理解，不等于执行前的硬性页面检查。

## 值得借鉴的功能

| 功能 | 优点 | 对工作台的建议 |
| --- | --- | --- |
| 策略附带适用条件与证据 | 能区分经验和猜测 | 第一优先：将快手案例转成策略卡片 |
| 同类技巧去重、限制容量 | 避免经验越积越乱 | 按应用、任务、页面类型归类；同类相似内容合并 |
| 策略替代与降级 | 旧办法失效后能退出使用 | 记录最后成功、失败次数、替代版本；新页面重新采样 |
| 试验与正式经验分开 | 避免一次偶然成功变成通用规则 | 复用工作台现有样本检查与真机试跑 |
| 失败分类、有限重试 | 区分方法失败、执行偏离、设备故障与结果不明 | 断线不算策略失败；结果不明先截图，不重放点击 |
| 中断恢复 | 保留未完成试验意图，不把崩溃直接算作失败 | 启动时先读取手机现状与未完成记录，再决定后续步骤 |
| 历史记录与重建检查 | 能追查策略何时被修改 | 在现有运行记录上关联策略编号与版本 |
| 条件等待、动作依赖 | 等条件成立再执行，少用固定长等待 | 借鉴结构，继续使用工作台执行器与同手机互斥 |
| 精简状态、按需读取细节 | 减少无关信息与模型耗时 | 已知页面用局部识别；异常再取完整画面 |
| 后台压缩对话 | 长任务压缩上下文时保留新消息 | 后期需要长时间模型运行时再考虑 |
| 独立评测与学习曲线 | 避免只看熟悉场景上的漂亮成绩 | 将不同广告版式留作验收；观察误触、完成率、耗时 |

## 不宜照搬的地方

- **“自动优化”效果不能照说明书直接认定。** `runOffline.ts` 没有把候选手册拿去重新跑游戏；`scoreCandidate()` 使用历史代理分数并可按失败案例数加分。首次还能允许无评分起步。它有版本晋升框架，但不能证明新版本实际更好。
- **离线反思目前是规则拼装。** `reflectMinibatch()` 按已有假设、技巧和失败摘要生成内容，未看到依据 `dryRun=false` 切换真实模型反思的实现。
- **提示文字不是安全限制。** 手机中的“不下载、不进入直播间”必须由执行流程限制，不能只写进经验提示。
- **文字量截断要改。** 注入函数末尾使用字符串截取，可能切断一条策略；受保护经验段也可能被后续长度截断。工作台应整条选取，禁止动作单独保留。
- **存储有边界。** 临时文件替换能减少写到一半的问题，但不等于多进程事务；部分读取错误回退为空库，不能直接照搬到重要经验库。
- **游戏可以固定地图重试，手机任务通常不能原样重来。** 不照搬自动A/B实验；先用已保存截图验证，再经小范围真机试跑。
- **游戏状态不是手机截图。** 该项目通过游戏内插件读取结构化信息，不靠连续截屏。不能将其性能直接推导为安卓截图提速，也不应向第三方手机应用植入同类插件。

## 建议的最小落地单位

先完成“快手策略卡片 + 已知页面调用”，暂不新增独立学习系统。

| 卡片内容 | 快手示例 |
| --- | --- |
| 识别依据 | 原任务计数、快手页面标志、直播预览文字 |
| 适用范围 | 已采样的荣耀竖屏页面；应用版本或版式变化需复核 |
| 允许动作 | 从直播入口按钮上方上滑 |
| 禁止动作 | 进入直播、关注、下载、安装、体验 |
| 成功依据 | 回到普通广告，原任务计数仍可读；跳过不算完成 |
| 异常出口 | 画面不符、计数回退或未知弹窗时停止并截图 |
| 证据与状态 | 关联本轮截图、运行编号、已验证状态和策略版本 |

实施顺序：整理少量卡片 → 用本轮截图检查识别 → 接现有工作流试跑 → 用户确认后本地提交。策略记录必须能关联到真正执行的流程版本，避免文档与执行脱节。

具体范围、保存方式与分阶段验收见 [工作台策略库方案](strategy-plan.md)。该方案尚未开发。
